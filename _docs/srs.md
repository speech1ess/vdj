## Спецификация требований к системе (SRS)  
### Playlist AI — Продвинутый медиаменеджер для DJ

**Версия**: 1.2  
**Дата**: 4 апреля 2025 года  
**Автор**: Grok (product manager) & speech1ess (solution architect)

---

### 1. Введение

#### 1.1 Назначение
Этот документ определяет требования к системе “Playlist AI” — продвинутому медиаменеджеру, предназначенному для помощи DJ в организации музыкальной библиотеки, анализе треков и генерации треклистов для выступлений. Система направлена на упрощение подготовки DJ сетов за счёт автоматизации анализа треков и подбора на основе заданных пользователем параметров.

#### 1.2 Область применения
Playlist AI будет предоставлять следующие основные функции:
- Сканирование и индексация музыкальной библиотеки пользователя (форматы FLAC, MP3, AIFF).
- Получение метаданных для треков (например, с Discogs).
- Анализ треков по параметрам: BPM, тональность, энергетика, настроение.
- Сохранение метаданных и результатов анализа в базе данных (SQLite для локального использования, PostgreSQL для удалённого) с возможностью кратковременного хранения в CSV.
- Генерация треклистов на основе заданных пользователем параметров (например, диапазон BPM, тональность, настроение, жанр, длительность треклиста, диапазон годов выпуска).
- Предоставление простого графического интерфейса для просмотра треков и сгенерированных треклистов с возможностью перехода на веб-интерфейс.
- Настройка параметров системы и базы данных через модуль конфигуратора, включая создание базы данных.

Первая версия (MVP) будет сосредоточена на базовой функциональности и простом интерфейсе, с возможностью дальнейшего расширения (например, веб-интерфейс, подключение стриминговых сервисов, SaaS-архитектура, анализ предпочтений пользователя).

#### 1.3 Определения, сокращения и аббревиатуры
- **BPM**: Beats Per Minute, темп трека (ударов в минуту).
- **Тональность**: Музыкальная тональность трека (например, соль минор).
- **Энергетика**: Уровень интенсивности трека (от 0 до 1).
- **Настроение**: Эмоциональный оттенок трека (например, “весёлое”, “грустное”).
- **FLAC/MP3/AIFF**: Поддерживаемые форматы аудиофайлов.
- **Discogs**: Онлайн-база данных музыкальных метаданных.
- **GUI**: Графический пользовательский интерфейс.
- **MVP**: Минимально жизнеспособный продукт.
- **MVVM**: Model-View-ViewModel, шаблон проектирования для приложений с GUI.
- **SQLite/PostgreSQL**: Системы баз данных для локального и удалённого хранения.
- **CSV**: Формат файла для кратковременного хранения данных (Comma-Separated Values).
- **Колесо Камелота**: Система для определения совместимости тональностей при гармоническом микшировании.
- **MoSCoW**: Метод приоритизации требований (Must have, Should have, Could have, Won’t have).

### 2. Общее описание

#### 2.1 Перспектива продукта
Playlist AI — это самостоятельное приложение, предназначенное для дополнения существующего DJ софта (например, Rekordbox, Traktor), с акцентом на подготовку к выступлениям. В отличие от Rekordbox или Traktor, которые в первую очередь ориентированы на микширование в реальном времени и управление контроллерами, Playlist AI фокусируется на:
- Глубоком анализе локальной музыкальной библиотеки пользователя.
- Автоматической генерации треклистов на основе заданных критериев.
- Лёгком и настраиваемом интерфейсе для управления треками с возможностью перехода на веб-интерфейс.

На первом этапе система будет десктопным приложением с использованием Tkinter, но архитектура будет спроектирована так, чтобы в будущем можно было легко переключиться на веб-интерфейс (например, с использованием Flask/FastAPI и MVVM) без значительного рефакторинга.

#### 2.2 Функции продукта
- **Сканирование музыкальной библиотеки**: Сканирование указанных директорий для поиска файлов FLAC, MP3, AIFF и их индексация.
- **Получение метаданных**: Извлечение метаданных (название, исполнитель, альбом, жанр, год выпуска и т.д.) через Discogs API.
- **Анализ треков**: Анализ треков по параметрам BPM, тональность, энергетика, настроение, длительность с использованием библиотек для анализа аудио (Librosa, Mutagen).
- **Хранение данных**: Сохранение метаданных и результатов анализа в базе данных (SQLite для локального использования, PostgreSQL для удалённого) с возможностью кратковременного хранения в CSV.
- **Генерация треклистов**: Создание треклистов на основе заданных пользователем параметров (например, диапазон BPM, тональность, настроение, жанр, длительность треклиста, диапазон годов выпуска).
- **Графический интерфейс**: Простой интерфейс для просмотра треков, фильтрации и отображения сгенерированных треклистов с возможностью перехода на веб-интерфейс.
- **Конфигуратор**: Модуль для проверки, настройки параметров системы и базы данных, включая создание базы данных.

#### 2.3 Классы пользователей и их характеристики
- **Основной пользователь**: Любители или полупрофессиональные DJ, которые хотят подготовить треклисты для выступлений.  
  - Характеристики: Знакомы с DJ софтом (например, Rekordbox), имеют большую локальную музыкальную библиотеку, ценят уникальную и не мейнстримную музыку, нуждаются в помощи с подбором треков для сетов.
- **Вторичный пользователь**: Музыкальные энтузиасты, которые хотят организовать и проанализировать свою музыкальную библиотеку.  
  - Характеристики: Не обязательно DJ, но интересуются метаданными и анализом треков.

#### 2.4 Среда функционирования
- **Платформы**: Windows, macOS (требуется кроссплатформенная совместимость).
- **Зависимости**:  
  - Python 3.8+  
  - Librosa, Mutagen (для анализа аудио).  
  - SQLAlchemy (для управления базой данных).  
  - Flask или Tkinter (для GUI).  
  - SQLite (локально), PostgreSQL (удалённо).  
  - Discogs API (для метаданных).  
- **Аппаратные требования**:  
  - Минимальные: 4 ГБ ОЗУ, процессор 1 ГГц, 500 МБ свободного места на диске.  
  - Рекомендуемые: 8 ГБ ОЗУ, SSD для более быстрого сканирования файлов.

#### 2.5 Ограничения проектирования и реализации
- Система должна быть кроссплатформенной (Windows, macOS).  
- Первая версия будет использовать SQLite для простоты; поддержка PostgreSQL будет добавлена позже.  
- Анализ аудио на начальном этапе будет опираться на Librosa и Mutagen (поддержка Essentia отложена из-за проблем с установкой).  
- Графический интерфейс будет минималистичным (Tkinter на первом этапе), но архитектура должна быть спроектирована так, чтобы минимизировать рефакторинг при переходе на веб-интерфейс с использованием MVVM (например, Flask/FastAPI + React).  

#### 2.6 Предположения и зависимости
- У пользователей есть локальная музыкальная библиотека в форматах FLAC, MP3 или AIFF.  
- У пользователей есть интернет-соединение для запросов к Discogs API.  
- Пользователи знакомы с базовыми понятиями (BPM, тональность, энергетика, колесо Камелота).

### 3. Функциональные требования

#### 3.1 Сканирование музыкальной библиотеки
- **Описание**: Система сканирует указанные пользователем директории для поиска файлов FLAC, MP3, AIFF и индексирует их.  
- **Приоритет (MoSCoW)**: Must have  
- **Функциональные требования**:  
  - Система должна позволять пользователю указать одну или несколько директорий для сканирования.  
  - Система должна определять файлы FLAC, MP3 и AIFF в указанных директориях.  
  - Система должна сохранять пути к файлам в базе данных.  
- **Входные данные**: Пути к директориям, указанные пользователем.  
- **Выходные данные**: Список проиндексированных файлов, сохранённый в базе данных.  

#### 3.2 Получение метаданных
- **Описание**: Система извлекает метаданные (название, исполнитель, альбом, жанр, год выпуска и т.д.) для каждого трека с использованием Discogs API.  
- **Приоритет (MoSCoW)**: Should have  
- **Функциональные требования**:  
  - Система должна запрашивать данные через Discogs API, используя имя файла трека или существующие метаданные (если они есть).  
  - Система должна сохранять полученные метаданные в базе данных.  
  - Система должна корректно обрабатывать ошибки API (например, ограничения по количеству запросов, отсутствие данных).  
  - Система должна поддерживать ручное редактирование метаданных пользователем (Should have).  
- **Входные данные**: Имя файла трека или частичные метаданные.  
- **Выходные данные**: Метаданные, сохранённые в базе данных.

#### 3.3 Анализ треков
- **Описание**: Система анализирует треки по параметрам BPM, тональность, энергетика, настроение и длительность с использованием библиотек Librosa и Mutagen.  
- **Приоритет (MoSCoW)**: Must have  
- **Функциональные требования**:  
  - Система должна анализировать BPM с помощью Librosa (`librosa.beat.tempo`).  
  - Система должна анализировать тональность с помощью Librosa (`librosa.feature.chroma_stft`).  
  - Система должна вычислять энергетику с помощью Librosa (`librosa.feature.rms`).  
  - Система должна оценивать настроение на основе спектральных характеристик (например, `librosa.feature.spectral_centroid`).  
  - Система должна определять длительность трека с помощью Mutagen.  
  - Система должна сохранять результаты анализа в базе данных.  
- **Входные данные**: Путь к аудиофайлу.  
- **Выходные данные**: BPM, тональность, энергетика, настроение, длительность, сохранённые в базе данных.  

#### 3.4 Хранение данных
- **Описание**: Система сохраняет метаданные треков и результаты анализа в базе данных с возможностью кратковременного хранения в CSV.  
- **Приоритет (MoSCoW)**: Must have (база данных), Could have (CSV)  
- **Функциональные требования**:  
  - Система должна поддерживать SQLite для локального хранения.  
  - Система должна поддерживать PostgreSQL для удалённого хранения (будущая реализация).  
  - Система должна использовать SQLAlchemy для абстракции базы данных.  
  - Система должна поддерживать экспорт данных в CSV для кратковременного хранения (например, для быстрого анализа или обмена).  
  - Система должна сохранять следующие поля для каждого трека:  
    - Путь к файлу (строка, уникальная).  
    - Название (строка).  
    - Исполнитель (строка).  
    - Альбом (строка).  
    - Жанр (строка).  
    - Год выпуска (целое число).  
    - BPM (число с плавающей точкой).  
    - Тональность (строка, например, “соль минор”).  
    - Энергетика (число с плавающей точкой, от 0 до 1).  
    - Настроение (строка, например, “весёлое”, “грустное”).  
    - Длительность (число с плавающей точкой, в секундах).  
- **Входные данные**: Метаданные треков и результаты анализа.  
- **Выходные данные**: Данные, сохранённые в базе данных или экспортированные в CSV.  

#### 3.5 Генерация треклистов
- **Описание**: Система генерирует треклисты на основе заданных пользователем параметров, включая жанр, длительность треклиста и диапазон годов выпуска.  
- **Приоритет (MoSCoW)**: Must have (основные параметры), Should have (жанр, длительность, диапазон годов)  
- **Функциональные требования**:  
  - Система должна позволять пользователю задавать параметры:  
    - Диапазон BPM (например, 120-130).  
    - Тональность (например, “соль минор” или “любая”).  
    - Энергетика (например, 0.7-1.0).  
    - Настроение (например, “весёлое”).  
    - Жанр (например, “диско”, “хип-хоп”).  
    - Длительность треклиста (например, 120 минут).  
    - Диапазон годов выпуска (например, 1980-1989 для диско 80-х).  
  - Система должна выбирать треки из базы данных, соответствующие заданным параметрам.  
  - Система должна сортировать треки для обеспечения плавных переходов (например, постепенное увеличение BPM, совместимость тональностей с использованием колеса Камелота).  
  - Система должна генерировать треклист, общая длительность которого соответствует заданной (с погрешностью ±5 минут).  
  - Система должна позволять сохранять и повторно использовать шаблоны параметров треклистов (Should have).  
- **Входные данные**: Параметры, заданные пользователем.  
- **Выходные данные**: Сгенерированный треклист, отображённый в интерфейсе.

#### 3.6 Графический интерфейс
- **Описание**: Система предоставляет графический интерфейс для просмотра треков, сгенерированных треклистов и настройки параметров.  
- **Приоритет (MoSCoW)**: Should have  
- **Функциональные требования**:  
  - Система должна предоставлять интерфейс с использованием Tkinter (десктоп) на первом этапе.  
  - Архитектура должна быть спроектирована с использованием MVVM, чтобы минимизировать рефакторинг при переходе на веб-интерфейс (например, Flask/FastAPI + React).  
  - Интерфейс должен отображать таблицу треков с колонками: Название, Исполнитель, Жанр, Год выпуска, BPM, Тональность, Энергетика, Настроение, Длительность.  
  - Интерфейс должен позволять пользователю фильтровать треки по BPM, тональности, энергетике, настроению, жанру, году выпуска или длительности.  
  - Интерфейс должен позволять пользователю вводить параметры для генерации треклиста (включая жанр, длительность, диапазон годов выпуска).  
  - Интерфейс должен отображать сгенерированный треклист.  
  - Интерфейс должен включать модуль конфигуратора для настройки параметров системы и базы данных.  
- **Входные данные**: Действия пользователя (фильтры, параметры, настройки).  
- **Выходные данные**: Отображённые треки, треклисты и настройки.  

#### 3.7 Модуль конфигуратора
- **Описание**: Система предоставляет модуль для проверки, настройки параметров системы и базы данных, включая создание базы данных.  
- **Приоритет (MoSCoW)**: Should have  
- **Функциональные требования**:  
  - Система должна предоставлять модуль конфигуратора, доступный через графический интерфейс.  
  - Модуль должен позволять пользователю:  
    - Указывать пути для сканирования музыкальной библиотеки.  
    - Выбирать тип базы данных (SQLite или PostgreSQL).  
    - Настраивать параметры подключения к PostgreSQL (хост, порт, имя базы, пользователь, пароль).  
    - Создавать базу данных PostgreSQL на основе определённых датаклассов (с использованием SQLAlchemy).  
    - Проверять доступность базы данных и Discogs API.  
    - Настраивать параметры анализа (например, точность определения BPM).  
  - Модуль должен сохранять настройки в конфигурационный файл (например, `config.ini`).  
- **Входные данные**: Параметры, введённые пользователем.  
- **Выходные данные**: Сохранённые настройки, результаты проверки (например, “база данных доступна”), созданная база данных.

### 4. Требования к внешним интерфейсам

#### 4.1 Пользовательские интерфейсы
- **Таблица треков**: Таблица, отображающая все проиндексированные треки с колонками: Название, Исполнитель, Жанр, Год выпуска, BPM, Тональность, Энергетика, Настроение, Длительность.  
- **Панель фильтров**: Поля ввода для фильтрации треков по BPM, тональности, энергетике, настроению, жанру, году выпуска или длительности.  
- **Форма генерации треклиста**: Поля ввода для диапазона BPM, тональности, диапазона энергетики, настроения, жанра, длительности треклиста и диапазона годов выпуска.  
- **Отображение треклиста**: Список треков в сгенерированном треклисте с указанием общей длительности.  
- **Модуль конфигуратора**: Форма для настройки параметров системы и базы данных (пути, тип БД, параметры подключения, создание БД).  

#### 4.2 Аппаратные интерфейсы
- Отсутствуют (система взаимодействует с локальным хранилищем файлов).  

#### 4.3 Программные интерфейсы
- **Discogs API**: Для получения метаданных треков.  
- **Librosa/Mutagen**: Для анализа аудио.  
- **SQLAlchemy**: Для работы с базой данных.  
- **Tkinter/Flask**: Для графического интерфейса.  

#### 4.4 Коммуникационные интерфейсы
- HTTP-запросы к Discogs API (для получения метаданных).  
- Подключения к базе данных (локальный файл SQLite, удалённый сервер PostgreSQL).

### 5. Нефункциональные требования

#### 5.1 Требования к производительности
- Система должна сканировать 1000 треков менее чем за 5 минут.  
- Система должна анализировать один трек (BPM, тональность, энергетика, настроение, длительность) менее чем за 10 секунд.  
- Система должна генерировать треклист менее чем за 2 секунды.  

#### 5.2 Требования к безопасности
- Система не должна раскрывать данные пользователя (например, пути к файлам, метаданные) третьим лицам.  
- Ключи Discogs API должны храниться безопасно (например, в переменных окружения).  

#### 5.3 Качественные характеристики
- **Удобство использования**: Интерфейс должен быть интуитивным для пользователей, знакомых с DJ софтом.  
- **Надёжность**: Система должна корректно обрабатывать некорректные аудиофайлы (например, пропускать их).  
- **Масштабируемость**: Система должна поддерживать до 10 000 треков в базе данных (для MVP).  
- **Поддерживаемость**: Код должен быть модульным и документированным с использованием Sphinx.  
- **Гибкость**: Архитектура должна минимизировать рефакторинг при переходе с Tkinter на веб-интерфейс с использованием MVVM.  

#### 5.4 Ограничения
- Система должна быть кроссплатформенной (Windows, macOS).  
- Система должна минимизировать использование ресурсов, чтобы работать на старом оборудовании.

### 7. Приложение

#### 7.1 Глоссарий
- **Треклист**: Список треков для DJ сета, упорядоченный для плавных переходов.  
- **Гармоническое микширование**: Подбор треков с совместимыми тональностями с использованием колеса Камелота для плавных переходов.  
- **Колесо Камелота**: Система для определения совместимости тональностей (например, треки в тональностях 1A и 2A совместимы).  

#### 7.2 Предположения
- У пользователей есть стабильное интернет-соединение для запросов к Discogs API.  
- У пользователей достаточно места на диске для музыкальной библиотеки и базы данных.
