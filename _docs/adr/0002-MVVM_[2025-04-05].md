# ADR 0002: Использование MVVM как архитектурного шаблона для GUI с Tkinter в MVP и переходом на веб в перспективе

## Контекст
Playlist AI требует графический интерфейс для MVP, который позволит пользователям сканировать треки, настраивать параметры, генерировать треклисты и просматривать статистику. В SRS указано использование Tkinter для десктопного GUI в MVP с планом перехода на веб-интерфейс (Flask/FastAPI + React) в будущем. Для MVP важны простота реализации и кроссплатформенность, но архитектура должна минимизировать рефакторинг при смене фронтенда. На данный момент GUI в процессе рефакторинга, реализованы представления (confvw, mainvw, scanvw, statvw) в Tkinter, включая функционал экспорта/импорта CSV в scanvw.


## Решение
Использовать **MVVM (Model-View-ViewModel)** как архитектурный шаблон для GUI:
- **Model**: Модели данных (AudioFile, Track, Album и др.), уже реализованные через SQLAlchemy ORM, обеспечивают доступ к данным.
- **View**: Представления Tkinter (confvw.py, mainvw.py, scanvw.py, statvw.py), отвечающие за отображение интерфейса и взаимодействие с пользователем (например, кнопки CSV в scanvw).
- **ViewModel**: Отдельный слой для бизнес-логики и обработки данных, связывающий View и Model. Реализация в процессе рефакторинга, предполагается вынести логику из view в ViewModel.
Tkinter используется для MVP как простой и встроенный в Python фреймворк, с архитектурой, позволяющей перейти на Flask/FastAPI + React в будущем.


## Альтернативы

- **MVC (Model-View-Controller)** — Подходит для десктопных приложений, но сложнее адаптировать под веб из-за сильной связи Controller с View.

- **Чистый Tkinter без шаблона** — Быстрая разработка для MVP, но логика смешивается с интерфейсом, что усложнит переход на веб.

- **Сразу веб (Flask + HTML)** — Избавляет от перехода, но требует больше усилий для MVP и внешних зависимостей.

- **PyQt** — Мощный фреймворк для GUI, но избыточен для pet-проекта и усложняет установку.


## Последствия

- MVVM разделяет логику и интерфейс, упрощая будущий переход с Tkinter на веб (ViewModel переиспользуется).

- Tkinter в MVP обеспечивает простоту разработки и кроссплатформенность без дополнительных зависимостей.

- Реализованные view (scanvw, mainvw и др.) уже работают, но рефакторинг нужен для выноса логики в ViewModel.

- ViewModel потребует дополнительного времени на реализацию, особенно для сложных операций (сканирование, генерация треклистов).

- Переход на веб потребует замены View (Tkinter → React), но Model и ViewModel останутся почти без изменений.

- Текущий рефакторинг GUI может замедлить прогресс MVP, но улучшит структуру кода.


## Статус
**Принято**
