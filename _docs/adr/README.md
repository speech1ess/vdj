# Документация ADR

## Описание

В этой директории хранятся **Architectural Decision Records** (ADR) — документы, описывающие архитектурные решения, их контекст, альтернативы и последствия для проекта.

Каждое решение имеет свой уникальный номер и название ПО, к которому оно относится. Формат имени файла:  
`<номер>-<название ПО>.md`

Пример:  
`0008-Prometheus.md`

## Структура

- **<номер>-<название ПО>.md** — файл, содержащий ADR. Название файла включает номер решения, название ПО.

## Как использовать

1. **Создание нового ADR**: Для того чтобы добавить новый ADR, создайте YAML-конфигурационный файл в директории `yaml/`, соответствующий вашему решению. [Пример структуры файла YAML для ADR](#пример-структуры-файла-yaml)
2. **Запуск генератора**: После добавления YAML-файла выполните скрипт `generate_adr.py` в корне проекта. Скрипт автоматически сгенерирует файл ADR и сохранит его в этой директории. Скрипт автоматически обновляет раздел [Список файлов с решениями](#список-файлов-с-решениями).
3. **Редактирование**: Каждый файл ADR можно редактировать вручную, чтобы добавить дополнительные замечания или уточнения.

## Стандарты
1. **"Documenting Software Architecture" (IEEE 1471/ISO/IEC 42010)**. Этот стандарт описывает принципы и практики для документирования архитектуры программного обеспечения, и хотя он не ориентирован исключительно на ADR, он помогает в контексте архитектурных решений. Основное внимание уделяется описанию архитектуры через различные виды и уровни абстракции, что помогает в ведении ADR.

2. **"The ADR Template" (или "Architectural Decision Records Template")**. Это не формальный стандарт, а шаблон, который используется для оформления ADR в удобном виде. Он был предложен в открытых источниках, например, в репозиториях GitHub, и часто используется как стандартизированное решение для записи архитектурных решений.
Стандартный шаблон ADR включает:
- Номер (уникальный идентификатор для каждого решения).
- Заголовок (краткое описание решения).
- Контекст (описание ситуации, которая потребовала решения).
- Решение (описание выбранного решения).
- Альтернативы (описание других рассмотренных решений).
- Последствия (последствия для системы, людей, процессов).
- Статус (например, принято, отклонено, ожидает решения).

## Примечания
Каждый ADR файл должен быть самодостаточным и содержать все необходимые разделы:

Context (Контекст)
Decision (Решение)
Alternatives (Альтернативы)
Consequences (Последствия)
Status (Статус)
Для более удобного поиска и организации решения могут быть объединены в категории или подкатегории, если количество ADR увеличится.

## Пример структуры файла YAML

Каждый файл YAML должен следовать следующему шаблону:

```yaml
number: "0008"
title: "Использование Prometheus для мониторинга"
context: "Нужно централизованное решение для сбора и анализа метрик."
decision: "Использовать **Prometheus** как основную систему мониторинга."
alternatives:
  - name: "Zabbix"
    reason: "Сложность настройки и масштабирования."
  - name: "Grafana Cloud"
    reason: "Облачный сервис, зависимость от внешнего провайдера."
consequences:
  - "Гибкость настройки и сбора метрик."
  - "Требуется развёртывание и поддержка серверов Prometheus."
status: "Принято"
```
