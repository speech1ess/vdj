# ADR 0001: Использование SQLAlchemy ORM с PostgreSQL как основой, SQLite как fallback и CSV для экспорта/импорта

## Контекст
Playlist AI ориентирован на обработку больших музыкальных коллекций (10,000+ треков) с использованием сложных аналитических алгоритмов. Система должна хранить метаданные треков (название, исполнитель, альбом, жанр, год) и результаты анализа (BPM, тональность, энергетика, настроение) в масштабируемой БД. При этом, также важна простота запуска и использования для средних коллекций (до 10,000 треков) и возможность экспорта/импорта данных для обмена или анализа. На данный момент уже реализован слой абстракции, описаны модели данных через SQLAlchemy ORM (AudioFile, Track, Album, Artist, Genre, Playlist и др.), идёт рефакторинг для записи в PostgreSQL, SQLite рассматривается как fallback-вариант и давно не тестировался. CSV уже работает в GUI для результатов сканирования.


## Решение
Использовать **SQLAlchemy ORM** как слой абстракции для работы с базой данных:
- **PostgreSQL** — основной вариант для хранения данных, обеспечивающий масштабируемость и производительность для больших коллекций.
- **SQLite** — fallback-вариант для средних коллекций (до 10,000 треков), встроенный в Python и не требующий настройки сервера.
- **CSV** — формат для экспорта/импорта данных, уже реализованный через кнопки "Сохранить в CSV" и "Загрузить из CSV" в GUI (Tkinter) для результатов сканирования.
Модели данных (track, audiofile, album, artist, genre и др.) уже описаны через SQLAlchemy ORM, что упрощает переключение между БД.


## Альтернативы

- **SQLite без ORM** — Простота для малых коллекций, но сложнее поддерживать реляционные модели и масштабировать.

- **Только PostgreSQL** — Мощная БД, но усложняет запуск для пользователей без установленного сервера.

- **MongoDB (NoSQL)** — Гибкость для неструктурированных данных, но избыточна для реляционной структуры треков.

- **Только CSV** — Простота экспорта, но не подходит для основного хранения из-за отсутствия транзакций.


## Последствия

- PostgreSQL с SQLAlchemy ORM обеспечивает масштабируемость для больших данных и сложных запросов (например, по жанрам и плейлистам).

- SQLite как fallback минимизирует зависимости для тестирования и средних коллекций.

- CSV в GUI экспортирует результаты сканирования (file_path, title, artist, album, genre, bpm, key) в %project_folder/data%, добавляя гибкость.

- Реализованные модели (AudioFile, Track и др.) ускоряют разработку, но рефакторинг для PostgreSQL требует доработки записи.

- PostgreSQL требует настройки сервера, что может быть барьером для пользователей.

- SQLite нужно протестировать после рефакторинга для подтверждения работоспособности.

- Миграции через Alembic понадобятся для поддержки обеих БД и обновления схемы.

- CSV пока не включает энергетику и настроение (energy_level, mood), что требует доработки анализа.


## Статус
**Принято**
